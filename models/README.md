# Models

`robotstudio_so101/` is a verbatim copy of `robotstudio_so101` from
[mujoco_menagerie](https://github.com/google-deepmind/mujoco_menagerie) at commit
`ac6b2b09983786f3036cab1000221017fa2193b4` (2026-05-18). Don't edit it. Put changes in `stage.xml` or a
task's objects file, so a menagerie update is a clean re-copy.

To re-vendor:

```bash
git clone --filter=blob:none --no-checkout https://github.com/google-deepmind/mujoco_menagerie /tmp/menagerie
cd /tmp/menagerie && git sparse-checkout set robotstudio_so101 && git checkout <sha>
rm -rf models/robotstudio_so101 && cp -r /tmp/menagerie/robotstudio_so101 models/
```

`stage.xml` includes the arm and adds what every scene shares:

- A compiler `meshdir` override. MuJoCo resolves `meshdir` against the top-level file, so the vendored
  `meshdir="assets"` would look in `models/assets/` without it.
- Timestep 1/300 s, so a 30 Hz control step is 10 physics steps. Menagerie ships 0.005 s.
- The `cube` and `bin_wall` default classes, so a cube behaves the same in every task.
- `base_collision`, a box standing in for the base. The MJCF base has visual meshes only, and menagerie
  removed the collision meshes on purpose. The box size came from the `so101` session, whose first try
  at 0.052 clipped the upper arm by 3.7 mm at rest.
- Lights and the ground plane.

Each task has a top-level scene in `models/` that includes `stage.xml` and then its own objects file. The
top-level file has to live here, because this is the directory `meshdir` resolves against.

- `scene.xml` is the bin-picking scene. `objects.xml` holds its table, with the top at z=0 where the arm
  base sits, a `front` camera aimed at `front_cam_target`, the cubes and the bin. The arm's own
  `wrist_cam` comes from menagerie.
- `search_scene.xml` is the mechanical-search scene: a table 10 cm or so below the base, a riser under
  the base, a deep bin and a pile of cubes. It and `search_objects.xml` are generated by
  `so101sim/search_layout.py`. Don't edit them by hand. `scripts/size_search_bin.py --write` rewrites
  them.

## Known mismatches with the hardware

The vendored arm carries a `camera_mount` body, 12 g, a child of `gripper` and a sibling of
`moving_jaw_so101_v1`. It is 2.4% of the mass distal to the shoulder and it sits at the longest lever the
arm has, about 270 mm from the base axis, worth 0.032 N·m of extra moment about the base. The `so101`
session cannot say whether anything is mounted there on the real arm, because nobody driving it has ever
seen it. What it does know: the RealSense has never streamed in any run, `pyrealsense2` is not installed,
and no camera appears in any configuration it has written. That rules out a camera being *used*. It says
nothing about whether a bracket is bolted on. Absent bracket, present but empty bracket, and menagerie
modelling something else entirely are all still open, and one glance at the arm settles it.

This is invisible to any measurement that fits actuator stiffness to a sag-versus-reach slope, because a
uniform change in gravity torque is degenerate with that gain. It is not invisible to payload margin with
something in the jaws, to dynamics at speed, or to the torque the real servos see. If a sim-planned
trajectory ever goes to hardware, decide deliberately whether to keep the body. Don't edit the vendored
model to remove it; override the mass from `scene.xml` or at load time, so re-vendoring stays a clean copy.

Don't use menagerie's `trs_so_arm100`. That's the older 5-DOF SO-100 with different geometry.
